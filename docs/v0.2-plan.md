# v0.2 plan: pydantic-ai model layer, Agent Skills instructions, less machinery

Status: implemented 2026-10-10 (this document is the design it was built to). v0.1 (commit
`d80681f`, to be tagged `v0.1.0`) is the baseline. Everything below is relative to it.

## The requirements this serves

From the owner:

> I want the language model, the caption-writing instructions (an Agent `SKILL.md` file), the
> data source and the output destinations to be injected/parameterised, so that I can use
> Gemini, Claude, GPT, OpenRouter-hosted models or local inference as the brain behind the
> captions while changing the shape of the captions to fit the model I'm planning to train. I
> want to read image data either from disk or a Hugging Face dataset and write the captions
> either to disk or the originating HF dataset to colocate them with the images.

And the operating stance: captions are low-stakes and get iterated on by running the tool
again. Guards against a current-generation model failing to follow clear instructions are not
worth their maintenance.

v0.1 meets the source/sink requirement. It does not meet the model requirement (three
hand-written adapters, no Claude, no OpenRouter), does not meet the instructions requirement
(policy baked into the package, assembled by Python, not user-suppliable), and carries a lot of
machinery the owner has now cut.

## Decisions

| Question | Decision |
|---|---|
| Model layer | pydantic-ai (`pydantic-ai-slim`). Every provider the owner named is one spec string. |
| Local inference | A vLLM server, `vllm:<model>` + `base_url`. No in-process path. |
| Instructions | Agent Skills spec directory, loaded **eagerly** by our own loader. Harness `Skills` rejected: it defers loading to the model's discretion. |
| Caption shape (profile) | Prose only: one Markdown file per trainer, living in the skill's `references/profiles/`. No code. |
| Structured output | pydantic-ai `output_type`, default mode `native`, per-endpoint override. |
| Critic | Optional. Runs only when the job names a `critic` endpoint. Approve or reject with notes; a rejection feeds back into the captioner once. |
| Mechanical checks | Exactly one: every mapped trigger appears in the caption and no unmapped trigger does. Nothing about format. |
| Resume | A caption that already exists is skipped unless `--overwrite`. One response record per captioned image is kept (the model's reply, the critic's verdict, which models served); no hashes. |
| Image handling | Keep the Pillow resize/re-encode (providers reject large images; metadata drops as a side effect). |
| Sources and sinks | The package's own protocols, simplified in interface, independently selectable. |

## Target architecture

```
job.yaml ──┬── skill: <dir>          ──► skills.load()    ──► Skill (body, references)
           ├── profile: <name|path>  ──► skill.profile()  ──► format + examples text
           ├── endpoints.captioner   ──► models.resolve() ──► Model + settings + output mode
           └── endpoints.critic      ──► models.resolve()     (optional)

prompt.captioner_instructions(skill, profile, job, mapping) ──► str
prompt.critic_instructions(skill, profile, job, mapping)    ──► str

Captioner = Agent(model, output_type=Caption,  retries=1)   + output validator: trigger check
Critic    = Agent(model, output_type=Critique)              (only if configured)

Runner: for each sample from the source ──► skip if sink has it ──► caption ──► [critique ──►
        feed back once] ──► sink.write
```

### 1. Model layer: `models.py`

```python
def resolve(spec: str | EndpointSpec) -> Resolved   # (Model, ModelSettings, output_mode)
```

- A spec string is any pydantic-ai `provider:model` string. The README documents `google:`
  (Gemini), `anthropic:` (Claude), `openai:` (GPT), `openrouter:<vendor>/<model>`,
  `vercel:<vendor>/<model>` (Vercel AI Gateway), `gateway/<provider>:<model>` (Pydantic AI
  Gateway) and `vllm:<model>`. Anything else goes to `infer_model` unchanged, so new providers
  need no code. Gateways are the recommended default for the app's audience: one key reaches
  every model, so a user shares one secret instead of four; the gateway host is fixed in code.
- `EndpointSpec.kind` is the provider prefix, spelled exactly as pydantic-ai spells it. No
  aliases. `kind: gemini` is a configuration error whose message names `google`.
- `vllm:` uses `VLLMProvider(base_url=…, api_key=…)`. `base_url` comes from
  `EndpointSpec.base_url` or `VLLM_BASE_URL`. Any other OpenAI-compatible server is also
  `kind: vllm` with a `base_url`; its key is `VLLM_API_KEY`, which the user set for custom
  endpoints and nothing else. `kind: openai` always talks to api.openai.com and refuses a
  `base_url`, because a job file can be downloaded and must never be able to redirect a stored
  provider key. A custom `base_url` must be https, or http only to a loopback, private-network or single-label host.
- Keys are read by the pydantic-ai providers from their own environment variables
  (`GOOGLE_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`,
  `VLLM_API_KEY`). The package has no secret-handling code of its own.
- `EndpointSpec.output_mode: native | tool | prompted`, default `native` (provider-enforced JSON
  schema; vLLM guided decoding). `prompted` for a server or OpenRouter upstream that rejects
  schema-constrained decoding; `tool` for models that do tool calls better than JSON mode.
- `Job.captioner_thinking` / `critic_thinking` map onto pydantic-ai's unified thinking setting.
  `EndpointSpec.settings` is a passthrough dict merged into `ModelSettings` (`temperature`,
  `seed`, `max_tokens`, vLLM `extra_body`, …).

### 2. Instructions: `skills.py` and the bundled skill

A skill is a directory per the Agent Skills specification:

```
my-captioning-skill/
  SKILL.md                      # frontmatter: name, description (required), metadata; body: the policy
  references/
    profiles/
      h3-still.md               # a profile: the trainer's caption shape, with examples
      flux-image.md
      ltx-image.md
      plain.md
    anything-else.md            # inlined only when metadata.references names it
```

- `skills.load(path) -> Skill` parses the frontmatter with PyYAML, validates `name` against the
  directory per the spec, returns the body and the directory. `Skill.profile(name_or_path)`
  returns the text of `references/profiles/<name>.md`, or of an arbitrary `.md` path, so a user
  can point at a profile outside the skill.
- `metadata.references: [file.md, …]` in the frontmatter names references to inline after the
  body on every run. Unnamed references are not read. (The spec's loaders never read bundled
  files; this is our one extension.)
- The bundled default skill is the current `policy/*.md` relocated: `core.md` plus the surviving
  part of `operating.md` become the `SKILL.md` body; the H3, FLUX and LTX sections of `h3.md` and
  `flux_ltx.md` become `references/profiles/*.md`, each with its worked examples from
  `examples.md` folded in; `sources.md` stays as provenance. Its `name` is
  `diffusion-training-captioner`. The job's `skill:` defaults to it.
- Loading is **eager**: the text goes into the agent's `instructions` on every run. Nothing is
  deferred. Other spec frontmatter fields (`allowed-tools`, `scripts/`, …) are accepted and
  ignored.

### 3. Assembly: `prompt.py` (replaces `policy/__init__.py` and `profiles/`)

```python
def captioner_instructions(skill, profile_text, job, mapping) -> str
def critic_instructions(skill, profile_text, job, mapping) -> str
```

Order: skill body → inlined references → profile text → job `policy_overrides` →
`ACTIVE JOB CONFIGURATION` JSON (`job.sample_view(mapping)`, unchanged) → task text. The task
text is two plain strings in `prompt.py`: the captioner's response contract (what the fields
mean, no schema dump; pydantic-ai supplies the schema) and the critic's task. The critic's user
turn carries the proposed caption and the image. Not configurable.

`POLICY_VERSION`, `policy_sha256` and the hash machinery are deleted. Nothing is bound to
anything.

### 4. Schemas: `schemas.py`

```python
class Caption(BaseModel):
    caption: str                 # the training text and nothing else
    usable: bool = True          # False: the mapped subject is absent/obscured/ambiguous
    note: str | None = None      # why, when not usable

class Critique(BaseModel):
    approved: bool
    notes: list[str] = []        # what to fix, when not approved
```

`PrimaryResult`, `Claim`, `CritiqueResult` and their self-report flags are gone.

### 5. Stages: `stages.py`

```python
captioner = Agent(model, name="captioner", output_type=Caption, retries=1, model_settings=…)

@captioner.output_validator
def triggers_present(ctx, result: Caption) -> Caption:
    # every trigger in ctx.deps.mapping appears as an exact token; no other job trigger does
    # on failure: raise ModelRetry("missing trigger NORA7" / "IVAN9 is not in this image")
```

- The user turn is `[USER_TURN, BinaryContent(data, media_type)]` with the image passed through
  `images.provider_image` first (resize to 3072 px / 8 MB, re-encode; EXIF drops).
- The trigger check is the one mechanical check. It uses the existing whole-token
  `exact_trigger_spans`. On failure pydantic-ai sends the message back to the model in the same
  conversation and asks once more. A second failure ends the run with the sample `rejected`.
- The critic, when configured, is `Agent(model, name="critic", output_type=Critique)`. Its run
  is single-turn: critic instructions, user turn = proposed caption text plus the image.
- The served model name is available on `result.all_messages()[-1].model_name`. It is logged in
  the summary as information. It fails nothing.

### 6. Runner: `runner.py`

```
for sample in source:
    mapping = job.mapping_for(sample.id)
    if mapping is None:                                 → needs_mapping   (no model call)
    if (await sink.record(sample.id) or {}).get("source") == "human":  → skipped
    if await sink.exists(sample.id) and not overwrite:  → skipped
    run = captioner.run(..., deps=mapping)
    if not run.output.usable:                           → unusable
    if critic:
        verdict = critic.run(...)
        if not verdict.approved:
            run = captioner.run("Reviewer notes: …", message_history=run.all_messages())
            verdict = critic.run(...)
            if not verdict.approved:                    → rejected
    await sink.write(sample.id, run.output.caption)     → written
```

Statuses: `written`, `skipped`, `needs_mapping`, `unusable`, `rejected`, `failed` (provider
error). `max_caption_attempts` is replaced by the fixed shape above: one trigger retry inside
the captioner run, one critic round-trip. Every sample that reached a model gets a response
record in the sink; the summary (`_summary.json` or stdout) lists each sample's status and notes. Concurrency is
the existing `asyncio.Semaphore`. `Runner.stream()` yields each `Outcome` as it completes;
`Runner.run()` collects them. Both take `only=` and `overwrite=` (see "Beyond v0.2").

### 7. Sources and sinks

```python
class ImageSource(Protocol):
    def samples(self) -> AsyncIterator[Sample]: ...

class CaptionSink(Protocol):
    async def exists(self, sample_id: str) -> bool: ...
    async def record(self, sample_id: str) -> dict | None: ...   # the stored response record
    async def write(self, sample_id: str, caption: str | None, record: dict) -> None: ...
    async def finalize(self) -> dict[str, Any]: ...
```

- The **response record** is one JSON object per captioned image: sample id, status, `source`
  (`model`, or `human` for a hand-edited caption, which the runner never overwrites), skill and
  profile names, the captioner's reply, the critic's verdict and notes, requested and served
  model names, attempt count. No hashes. `SidecarSink` writes it as `<stem>.json` beside
  `<stem>.txt`; `HFDatasetSink` as a `<caption_column>_response` JSON-string column.
- Source and sink are chosen by flag: `--images DIR` or `--repo ID` in; `--out DIR` or
  `--to-repo ID` out, defaulting to the originating repo when the source is a dataset. All four
  combinations work; `hf run` is gone because `run --repo` is the same thing. `--overwrite` and
  `--only ID...` on `run`.

### 8. Job file after v0.2

```yaml

profile: h3-still                   # a profile in the skill's references/profiles/, or a path to a .md
concepts: [...]                     # unchanged

  captioner: { kind: google,     model: gemini-3.8-flash }
  critic:    { kind: vllm,       model: Qwen/Qwen3-VL-32B-Instruct, base_url: http://localhost:8000/v1 }
  # critic absent → no critic pass
  # or:      { kind: anthropic,  model: claude-opus-5-5 }
  # or:      { kind: openrouter, model: anthropic/claude-sonnet-4-6, output_mode: prompted }
```

Removed `Job` fields: `require_model_match`, `minimum_caption_words`, `max_caption_attempts`.
`EndpointSpec` gains `base_url`, `output_mode`, `settings`; loses `retries`, `min_interval`.

## Beyond v0.2: the macOS app and remote GPUs

Settled with the owner on 2026-10-10. The audience is someone with a MacBook on factory
settings, not a Linux user. So:

- **The product is a native macOS app in Swift / SwiftUI.** It must be installable as a signed,
  notarized `.dmg` with no terminal, no Python runtime and no environment variables. API keys
  (model providers, Hugging Face, the GPU provider) live in the Keychain behind a settings
  screen.
- **The app never needs a GPU.** Training, local captioning with vLLM and anything CUDA runs on
  a rented pod. The app curates data, pushes it to the Hub, provisions the pod, launches runs
  and watches them.
- **This Python package is the reference implementation and the CLI**, kept for terminal users
  and as the spec the Swift port is written against. The job file, the skill directory, the
  profile files and the response record are the shared contract; they are language-neutral and
  must not grow Python-only features.

### What the app does

Screens, in the order a first-time user meets them: pick images (folder or Hub dataset) →
define concepts and triggers → map subjects per image (see the image, type a locator per
trigger; `Job.set_mapping` / `Job.save` semantics) → choose model, skill and profile → caption,
with live per-sample outcomes (`Runner.stream` semantics) → review and edit captions, mark one
final (`source: human`), re-caption a selection, compare two models side by side → push the
dataset → provision a pod and launch training → watch TensorBoard → collect the LoRA.

The captioning pipeline is ported to Swift natively: skills loader, prompt assembly, trigger
check, runner, sidecar and Hub sinks, and three thin HTTP clients (Gemini, Anthropic, any
OpenAI-compatible endpoint, which covers OpenAI, OpenRouter and vLLM) with JSON-schema output.
Hosted-API captioning therefore needs no pod at all.

### Remote GPUs

A `GPUProvider` abstraction in the app, RunPod first (REST v2), others later: list GPU types and
prices, create a pod from one of our images with N GPUs, a network volume and exposed ports,
poll status, fetch the proxy URL for a port, stop, terminate. The app shows the hourly price
before creating anything and never leaves a pod running without the user seeing it.

**Our own container images.** One base image: CUDA, vLLM, TensorBoard and a small control
agent that exposes an HTTP API on the pod: start or stop a service on a given set of GPUs,
report status and logs, tail event files. Trainer-specific images layer on top of the base
(the H3 / AI Toolkit trainer, the LTX trainer, a FLUX trainer). Everything the app does on a
pod goes through the control agent; it never shells in.

**GPU topology rule.** The app reads the pod's GPU count and plans the run:

| GPUs | Captioning | Training |
|---|---|---|
| 1 | vLLM on GPU 0, then stopped to free VRAM | the trainer on GPU 0, after captioning finishes |
| 2 or more | vLLM pinned to GPU 0 for the whole session | the trainer on GPUs 1..N-1 |

Sequential on one GPU, concurrent on two or more. The same rule lets a user re-caption during a
training run on a multi-GPU pod. The control agent enforces GPU assignment with
`CUDA_VISIBLE_DEVICES` per service; the app never computes it twice.

**Data flow.** The Hub is the handoff. The app pushes images, captions, response records and
`job.yaml` to a dataset repo; the pod pulls that repo; training writes the LoRA, samples and
TensorBoard event files to the network volume and pushes the LoRA to a model repo. TensorBoard
runs on the pod, listens on loopback only, and is shown in the app through the control agent's
authenticated `/tensorboard/` route (bearer on first load, then a cookie scoped to that path);
it has no exposed port of its own. *(Decision carried in from the pod work, 2026-10-10: the pod
brief requires everything on the pod to be reachable only over the authenticated API; see
POD-SPEC §2.1.)*

### Photos, Google services and LLM-assisted mapping (ordering approved 2026-10-10)

Neither Apple Photos nor Google Photos exposes who is in a picture to any app: PhotoKit blocks
the People album, Vision detects faces but does not recognise them, and Google Photos never
exposed face groups and since 2025-03-31 only lets apps read media they created (browsing goes
through the Picker API). So "subject mapping from the service" is not available anywhere; the
value is in the helpers around it.

**v1 (in the first app release):**

- **Apple Photos import** via PhotoKit: pick an album or a selection, pull iCloud originals on
  demand, optionally write the finished dataset back as an album. Sandbox entitlement
  `personal-information.photos-library`.
- **Vision helpers, on-device:** face detection and crops; feature-print similarity so that one
  labelled face per trigger proposes the same person across the set; near-duplicate detection;
  face capture-quality and aesthetics scores; text detection to flag images with readable signs
  or logos (the policy tells the captioner to avoid quoting them); face-centred crop suggestions
  for identity LoRAs.
- **LLM-proposed mapping from reference images:** the user gives one reference face per trigger;
  the model is shown the reference(s) and each image and proposes which trigger is where plus a
  locator sentence; the user confirms per image. Provider-agnostic (works through Gemini, Claude,
  GPT or a gateway); this is the main friction remover in the mapping step.
- **LLM-drafted boundary decisions** from a plain-language description of what the LoRA should
  learn, and a **dataset-level critique** before training ("all 40 images share the same jacket").

**Later:**

- **Video training-data workflow (approved 2026-10-11):** import clips, select/trim segments,
  inspect frames over time, map concepts per segment, and write motion-aware captions. Trainer
  inputs must match the chosen segments. This is separate from existing still-image training
  routes for video models such as MiniMax H3.
- Google Photos through the **Picker API**, run once per concept ("pick photos of NORA7") so the
  user can lean on Google's own face search to pre-label the selection.
- Google Drive with the unrestricted **`drive.file`** scope only (files the app created or the
  user picked): "keep my project in Drive".
- Gemini **Batch API** for large datasets at reduced price (a Swift client can; pydantic-ai does
  not).

**Never:** the full Drive scope (restricted; verification plus a paid security assessment above
a hundred users), or any attempt to read Photos' people data.

### What v0.2 leaves room for, and does

- The job, skill, profile and record formats are the app's formats. No Python-only fields.
- `Runner.stream()` with `only=` and `overwrite=`, `Job.unmapped()`, `set_mapping()`,
  `save()`, and `source: human` in the record: the semantics the app reproduces.
- `vllm:` with a `base_url` is exactly how the app will talk to GPU 0 on a pod.
